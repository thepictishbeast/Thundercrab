# ThunderCrab Additive Per-User Personalization — Implementation Blueprint

This is ONE merged spine, not four designs. Six cross-cutting decisions resolve the collisions; everything downstream inherits them.

## Decision Record (resolves critique X1–X4 + guardrails)

- **D-STORAGE (X1/1a/1b):** Profile lives in **local SQLite, account-keyed, offline-first**. The IMAP-header-carried profile is **rejected**: verified at `rust_imap.rs:418-424` `parse_headers` unfolds continuation lines by injecting a space and `push_if_relevant` joins them — a folded 16 KiB base64 header is corrupted on read; and `thundercrab-core/Cargo.toml` has no base64 *decoder* (the only base64 in-tree is the private encoder-only fn at `managesieve.rs:292`). Server sync is a later, separate transport (see §4), not the local store.
- **D-RULESTORE (X2):** Single owner for routing rules = the existing `rules` table (origin=User) + a new `rule_editor_meta(enabled, ordinal)`. The profile does **NOT** embed a duplicate `Vec<CrabRule>`. The serde `Profile` blob covers **layout + folder-overlay only**; routing is referenced by id.
- **D-SCHEMA (X1):** **One** `SCHEMA_VERSION 1→2` bump. All new tables created in the single `init()` `execute_batch` (additive, `CREATE TABLE IF NOT EXISTS`, consistent with `db.rs:83-135`). Not four parallel "version 2"s.
- **D-FFISHAPE (X3):** Flat typed `uniffi::Record`/`uniffi::Enum` (the `FfiAccountConfig`/`FfiFlagEvent` pattern, `lib.rs:271,440`). Opaque JSON strings **only** for `when_json`/`action_json`. No whole-profile-as-String blob (that would force Kotlin to parse/interpret profile JSON = logic in the thin layer the FFI banner forbids, `lib.rs:7-11`).
- **D-ISOLATION (X4):** Every **new** table is account-keyed `account = format!("{imap_host}|{username}")`, derived in **one** FFI fn `personalization_account_id`. The legacy `rules`/`flag_events` tables get an **additive `account TEXT` column in the same 1→2 migration**, backfilled to a sentinel `""` (= "unscoped/legacy") so existing rows survive and new writes are scoped. This satisfies the HARD CONSTRAINT "stored independently per user" without a destructive rewrite. (Rationale stated, not silently inherited.)
- **D-GUARDRAILS:** (a) user-edited rules pass a **new** `validate_user_rule` (NOT `apply_suggestion`, which clamps `1..=49`/forces Federated, verified `safety.rs:82-93`); (b) **no** direct Sieve push to a separate active script — SETACTIVE is single-script (`managesieve.rs:146-159`) so activating `thundercrab_personal` would deactivate Mailroom's = breach additive; server-side rule application is **Strategy A** (Mailroom `POST /rules`, `SERVER-COUPLING.md:93-97`, RECOMMENDED); (c) **no `pushSieve` on the Android Repository** (deliberate AVP-2 guardrail, `ThunderCrabRepository.kt:60-65,99-100`).

`eval::evaluate` (§7 port) is **in scope** as a prerequisite only for "test against recent". The "why is this here?" explainer is **free** via `X-PlausiDen-Category` already present in `other_headers` — no port needed for it.

## 1. Unified per-user profile data model (versioned Rust types + serde)

New module `thundercrab-core/src/personalization.rs` (export from `lib.rs` as `pub mod personalization;`). Pure serde, no IMAP/FFI deps. The `Profile` carries layout + folder-overlay only (routing is owned by the `rules` table per D-RULESTORE).

```rust
/// Document format version. Bumped only on a breaking shape change;
/// additive fields use #[serde(default)] (forward-compat). A profile read
/// with format_version > PROFILE_FORMAT_VERSION is rejected
/// (ProfileError::FormatTooNew), mirroring Db's SchemaTooNew gate (db.rs:122).
pub const PROFILE_FORMAT_VERSION: u32 = 1;

#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
pub struct Profile {
    #[serde(default = "default_format_version")] pub format_version: u32,
    /// Monotonic server-sync generation (server is the revision authority, §4).
    #[serde(default)] pub doc_revision: u64,
    #[serde(default)] pub layout: Section<LayoutPrefs>,
    #[serde(default)] pub folders: Section<FolderOverlay>,
    // NOTE: NO routing field. User rules live in the `rules` table (D-RULESTORE).
}

/// Per-section version + edit clock. Scalars reconcile LWW by (version,
/// updated_at); collection sections reconcile by element-union (§4, fix 1d).
#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize, Default)]
pub struct Section<T> {
    #[serde(default)] pub version: u64,
    #[serde(default)] pub updated_at: i64,   // UTC epoch seconds
    #[serde(default)] pub data: T,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq, Default, Serialize, Deserialize)]
#[serde(rename_all = "snake_case")]
pub enum ThemeMode { #[default] System, Light, Dark }   // -> ThundercrabTheme.darkTheme

#[derive(Debug, Clone, Copy, PartialEq, Eq, Default, Serialize, Deserialize)]
#[serde(rename_all = "snake_case")]
pub enum Density { Compact, #[default] Comfortable, Spacious }

#[derive(Debug, Clone, Copy, PartialEq, Eq, Default, Serialize, Deserialize)]
#[serde(rename_all = "snake_case")]
pub enum SortOrder { #[default] DateDesc, DateAsc, SenderAsc, UnreadFirst }

#[derive(Debug, Clone, Copy, PartialEq, Eq, Default, Serialize, Deserialize)]
#[serde(rename_all = "snake_case")]
pub enum SwipeAction { None, #[default] ToggleRead, ToggleFlag, Move, Archive }

#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
pub struct LayoutPrefs {
    #[serde(default)] pub theme_mode: ThemeMode,
    #[serde(default = "default_true")] pub amoled_black: bool,   // AMOLED doctrine default
    #[serde(default)] pub dynamic_color: bool,
    #[serde(default)] pub density: Density,
    #[serde(default = "default_subject_lines")] pub subject_lines: u8, // clamped 1..=3
    #[serde(default = "default_true")] pub show_sender_line: bool,
    #[serde(default)] pub sort_order: SortOrder,
    #[serde(default = "default_swipe_left")] pub swipe_left: SwipeAction,   // Archive
    #[serde(default = "default_swipe_right")] pub swipe_right: SwipeAction,  // ToggleRead
    #[serde(default)] pub default_folder: Option<String>,
}
// "preview lines" is reinterpreted as subject_lines (SUBJECT wrap, never a body
// snippet) — no-body invariant. Default impl returns the doctrine defaults.

/// Presentation-only overlay on list_folders(). NEVER an IMAP mutation, never a
/// copy of the Mailroom baseline. created[] registers display-name metadata for
/// folders the user made on-device; actual CREATE/RENAME/DELETE is §2 imap ops.
#[derive(Debug, Clone, PartialEq, Eq, Default, Serialize, Deserialize)]
pub struct FolderOverlay {
    #[serde(default)] pub created: Vec<UserFolder>,  // {server_path, display_name}
    #[serde(default)] pub pinned: Vec<String>,       // server paths, top of list
    #[serde(default)] pub hidden: Vec<String>,       // filtered from UI only
    #[serde(default)] pub order: Vec<String>,        // explicit order; empty = server order
    #[serde(default)] pub collapsed: Vec<String>,
}

#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
pub struct UserFolder { pub server_path: String, pub display_name: String }

#[derive(Debug, Error)]
pub enum ProfileError {
    #[error("profile format {found} newer than supported {supported}")]
    FormatTooNew { found: u32, supported: u32 },
    #[error("json: {0}")] Json(#[from] serde_json::Error),
}
```

- `Profile::default()` / `Profile::new()` → format_version=PROFILE_FORMAT_VERSION, doc_revision=0, both sections version=0 with `T::default()`.
- `Profile::sanitized(self) -> Profile` clamps `subject_lines` to `1..=3` and dedups overlay vecs (defense against malformed synced/edited docs). BUG ASSUMPTION: pure, total, no I/O.
- `pub fn reconcile(local: &Profile, remote: &Profile) -> Profile` (§4 semantics).
- No `deny_unknown_fields` framing (critique 1e: that default does not exist anywhere in-tree). Forward-compat comes purely from `#[serde(default)]` per field.

## 4. Server sync + additive-separation design

**Local-first ship state.** The profile lives in the per-user `profile` row (`account` PK); user rules in `rules` (account-scoped). Nothing leaves the device by default → no conflict, no PII transmitted.

**Where per-user state goes on prime (when sync ships):** **Strategy A**, per `SERVER-COUPLING.md:93-97,106` (RECOMMENDED). Rules: client POSTs the safe `CrabRule` JSON to Mailroom `POST /rules`; the server merges into the user's **additive personal layer** and re-emits via `to_sieve_with`. The server stays the **sole Sieve author** for the shared baseline; the client never writes Sieve → **no clobber possible**. Layout/folder-overlay sync: a sibling per-user `GET/PUT /profile` carrying the same canonical JSON (same wire format).
The **IMAP-header storage location is explicitly rejected** for the reason in D-STORAGE (folding corrupts the payload; no decoder in core).

**Reconciliation (pull → reconcile → push, optimistic concurrency):**
1. Pull → `remote` Profile + its `doc_revision`.
2. `reconcile(local, remote)`:
   - **Scalar sections (layout enums/bools):** LWW by `(version, updated_at)`.
   - **Collection fields (folders.created / pinned / hidden / order / collapsed; user-rule set):** **element-union keyed by stable id/path** — this is what "additive" literally means (fix 1d). A folder/rule added on device A and a different one on device B both survive; no whole-section clobber. Order vec merges by appending unseen paths.
   - `doc_revision = remote.doc_revision` (server is revision authority); `format_version = max`; run `sanitized()`.
3. Push with `expected_doc_revision = remote.doc_revision`; if the server moved on, re-pull/re-reconcile/retry once, then surface to UI. `format_version` newer on remote → `FormatTooNew`, sync paused, prompt to update (never silent downgrade).

**Additive separation (end-to-end):** the `Profile` type has **no field mirroring** `CategoryRules::deployed()`; no code path reads or writes the baseline. RoutingRules are origin=User only (Platform/Federated never enter the personalization doc). Folder overlay layers over live `list_folders`; removing the profile returns the raw server view with zero residue.

## 5. Security notes

- **No bodies:** the layer adds no body fetch. Folder ops are namespace-level (CREATE/RENAME/DELETE/SUBSCRIBE) + STATUS/LIST/LSUB. Rule test/eval reuse already-fetched `BODY.PEEK[HEADER]` data (`rust_imap.rs:260`). `fetch_body`'s `NotImplemented` gate (`ffi/lib.rs:1003`) is untouched. `subject_lines` controls SUBJECT wrap only, never a body snippet.
- **Per-user isolation:** every new table is account-keyed; legacy tables gained an additive `account` column (D-ISOLATION). Account id derived in one FFI fn. Two accounts on one device cannot read/overwrite each other's profile/rules. Server-side, Strategy A keeps each user's additive layer separate.
- **No PII to telemetry/federation:** new `DiagKind` events carry op-label + numeric counts only — **folder/rule names MUST NEVER appear in a `DiagEvent`** (enforced by the payload-free `timed()` wrapper, `lib.rs:148-166`; call it out in review). Profile/overlay never written to `core::telemetry` or `crab-ledger`.
- **Sieve safety gate:** user-edited rules pass `validate_user_rule` (new) — reuses `is_safe_match` + protected-folder/flag floor, keeps origin=User/score≥100. The profile **holds** rules as data; it does not apply them. Server application is Strategy A only — **no direct `push_sieve`**, so Mailroom's active script is never clobbered (SETACTIVE single-script breach avoided). Folder management has no managesieve dependency (add a test asserting this).
- **Integrity via auth+TLS:** no profile signing (Ed25519 stays for the federated ledger's cross-install trust — different threat model). Local DB inherits the 0600 posture of `thundercrab.db`; no new secret/credential column.

## 6. Defer

- **managesieve `LISTSCRIPTS`/`GETSCRIPT` + direct separate-script push** (`thundercrab_personal`). Only serves the rejected direct-push path; SETACTIVE is single-script so it can't coexist additively without Sieve `include` (server-varying). Server-side rule application is Strategy A.
- **Android `pushSieve` / live server write** — deliberate AVP-2 guardrail (`ThunderCrabRepository.kt:60-65`). Stays out of the Repository contract; gate any future live push behind explicit operator consent + throwaway test account (ROADMAP P2).
- **Mailroom `POST /rules` + `GET/PUT /profile` endpoints** (P2). Auth scheme (mailbox creds vs PlausiDen session token) is an open question for paul — do not invent a scheme.
- **Server profile mirror transport** (JMAP blob vs per-user prefs object). Local-first ships first; the reconciliation logic above is ready for it.
- **Retrofitting `rules`/`flag_events` to full multi-account UX** (account switcher, per-account stores in the UI). The additive `account` column lands now; the multi-account surface is later.
- **Orphaned-rule auto-cleanup on folder delete** — v1 is **warn-only** (list affected `FileInto{folder}` rules, let user retarget/delete); never auto-edit a rule or auto-push.
- **Profile export/import as a portable file** — nice-to-have once local model is stable.
- **Soft-delete/undo for folder delete** beyond the confirm dialog.

# Adversarial Architecture Critique — ThunderCrab Personalization Layer

Findings are grounded in the actual source (file:line cited). Ordered: cross-cutting first (these are invisible to per-design review), then per-design. Severity: **[BLOCKER]** = won't work / breaches a hard constraint as specified; **[MAJOR]** = significant gap or doctrine violation; **[MINOR]** = correctness nit / overclaim.

## Cross-design (the four designs are ONE layer and collide)

**X1 [BLOCKER] — SCHEMA_VERSION collision.** All four designs independently bump `SCHEMA_VERSION 1→2` (db.rs:59) and add a *different* new table (D1 `profile`; D2 `folder_prefs`; D3 `rule_editor_meta` + `personal_sync`; D4 `layout_prefs`). They cannot all be "version 2." `init()` (db.rs:83-135) creates tables unconditionally via `IF NOT EXISTS`, so the version number is only a marker — but four designs each asserting "the 1→2 additive migration" means the *shipped* schema is some superset none of them describe. This needs one coordinated migration plan (or sequential 2/3/4/5), not four parallel "version 2"s.

**X2 [MAJOR] — Routing rules get two sources of truth with no reconciliation.** D1 stores user routing rules inside `profile.routing` (`RoutingRules{rules: Vec<CrabRule>}`); D3 stores them in the existing `rules` table plus a new `rule_editor_meta(enabled, ordinal)`. A D1 profile *restore* writes `CrabRule`s back but carries no `enabled`/`ordinal` — so a cross-device restore silently drops disable-state and visual ordering that D3 owns. Conversely D3's editor "mirrors origin=User rules into the profile's RoutingRules" (D3 android_ui) but the profile has no slot for meta. Two stores, divergent shapes, no defined merge. Pick one owner for user rules.

**X3 [MAJOR] — FFI shape inconsistency for layout prefs (logic leaks into the thin layer).** D1 carries the *entire* profile (including layout) as one opaque `profile_json: String`; D4 carries layout as flat typed `FfiLayoutPrefs` enums/scalars. D4 matches the codebase convention: `FfiAccountConfig`/`FfiFlagEvent`/`FfiFolder` are flat `uniffi::Record`s (lib.rs:271, 440, 330); opaque JSON is reserved *only* for the recursive `when_json`/`action_json` AST (lib.rs:537-553), with an explicit doctrine reason. D1's blob forces the Kotlin Repository to parse and interpret profile JSON to render a settings form — that is exactly the "real logic in the thin layer" the FFI module banner forbids (lib.rs:7-11). D4's typed seam is correct; D1's whole-profile-as-string is a doctrine violation for the layout/folder portions.

**X4 [BLOCKER] — Per-user local isolation does not exist today; three designs assume it.** AppContainer.kt:27 defines a *single* `thundercrab.db`, and `rules`/`flag_events` are NOT account-keyed (db.rs:88-107). D3 security asserts "one DB per account profile, never shared" — **false**. D1 stores per-user routing rules in a per-user profile while the underlying `rules` table is global-per-device — internally inconsistent. Only D2 and D4 confront this: D2/D4 add an `account` / `account_id` key to *their* new table, but then create a documented asymmetry (prefs are per-account; rules/events are not). D1/D3's "additive & per-user, stored independently per user" hard constraint is satisfied server-side (IMAP-folder isolation in D1 holds) but NOT locally. The local per-user story needs to be designed, not assumed.

## Design 1 — Per-user Personalization Profile (IMAP-header storage)

**1a [BLOCKER] — The headline storage mechanism does not round-trip.** D1 stores the profile as base64 in a custom header read back via "the SAME `parse_headers` path" and claims it's "fold-safe." Both are contradicted by the code D1 cites. `parse_headers` (rust_imap.rs:430-436) *unfolds* continuation lines by inserting a `' '`: `value.push(' '); value.push_str(line.trim_start())`. A 16 KiB base64 string cannot live on one header line (RFC 5322 caps lines ~998 octets; servers fold or reject). On read, unfolding injects spaces *into the base64*, and standard base64 decode then fails. `from_header_value` as specified does not strip whitespace before decode. The "fold-safe (only base64 alphabet + CRLF-folding)" claim is wrong — folding is exactly what breaks it. This is a "doesn't work as written," not a nit.

**1b [BLOCKER] — No base64 dependency or decoder exists.** The workspace has no `base64` crate (verified against Cargo.toml). managesieve.rs:304 hand-rolled a base64 *encoder* (private, encoder-only, no decoder). D1's `from_header_value` base64-*decode* has nothing to call. Either add a dependency (against the "vendor-cost vs hand-roll" posture stated in managesieve.rs:13-17) or hand-roll a decoder — not the "free" reuse claimed.

**1c [MAJOR] — `canonical_json_bytes` reuse crosses a crate boundary that doesn't exist.** D1 puts `profile.rs` in `thundercrab-core` and says to "reuse the ledger's sorted-key `canonical_json_bytes`." That helper is a *private* fn in `thundercrab-suggestions::ledger` (ledger.rs:169) and again private in `crab-ledger::api` (api.rs:375). `thundercrab-core` does not depend on `thundercrab-suggestions` (and must not — suggestions depends on core). Reusing it means *moving* it down into core first. Real, unscoped work.

**1d [MAJOR] — Section-level LWW is not "additive"; it loses concurrent within-section edits.** D1 sells per-section `(version, updated_at)` LWW as "additive doctrine realized as mechanism." But the additive payloads are *collections*: `RoutingRules{rules: Vec<…>}`, `CustomFolders{created: Vec<…>}`. Two devices each adding a *different* rule/folder between syncs → reconcile takes the whole higher-versioned section and the other device's addition is **lost**. It's additive *across* sections, not *within* them — and within is exactly where concurrent additive edits land. This is the sync/conflict bug the design claims to have solved.

**1e [MINOR] — `deny_unknown_fields` justification is factually wrong (conclusion is fine).** D1 calls the Profile "the ONLY type exempt from the project-default `deny_unknown_fields`." That default does not exist anywhere in the tree (verified: zero occurrences; even `CrabRule` does not deny unknowns — crab_rule.rs:81). The *behavior* D1 wants (a synced, version-evolving doc tolerating unknown fields) is correct; the premise that it's a deliberate exception to an established default is false. Drop the "only exempt type" framing.

**1f [MINOR] — `append` is unverified here.** D1 calls APPEND "the one genuinely new IMAP primitive." async-imap 0.11.2 is confirmed (Cargo.lock) but its source isn't extracted on this host, so I could not byte-verify `Session::append`. Treat as "claimed, source-unverified" before building on it.

## Design 2 — Graphical Folder Management

**2a [MAJOR/positive] — This is the most code-grounded design and the only one that confronts the local-isolation gap honestly** (account-keyed `folder_prefs`, open_question on the rules/flag_events asymmetry). The `\HasChildren`/`delimiter` capture is correctly identified as new (FolderEntry::from_list, rust_imap.rs:134-164, captures neither today). The `lsub` second-pass for subscription state is a reasonable read.

**2b [MINOR] — "Backend trait stays minimal" / adding methods is fine, but note RPITIT.** D2 adds four ops to the `Backend` trait "mirroring move_message's signature shape." That's correct and compiles — the trait uses `impl Future` RPITIT (lib.rs:150-187) and is consumed concretely via `RustImapBackend`, wrapped by the FFI Object (lib.rs:803-806). No object-safety problem. (Flagging because a reviewer might wrongly call RPITIT a blocker — it isn't.)

**2c [MAJOR] — Orphaned-rule-on-delete is correctly raised but the safe default is under-specified.** D2 notes deleting a folder orphans a `CrabRule{FileInto{folder}}` and that emitted Sieve `fileinto :create` silently re-creates it. Good catch. But D2 leaves it "warn-only, confirm for v1" — given the ADDITIVE/no-clobber doctrine, the design should *commit* to warn-don't-auto-edit (never auto-rewrite a user rule, never auto-push), not defer the decision.

**2d [MINOR] — Telemetry leak risk is real and well-flagged.** Folder names are user data; the existing `timed()` records counts only (lib.rs:148-166) and `DiagEvent` has no string-payload field for names. D2's "static-op-label-only" rule is consistent with the code. Keep it as a review gate.

## Design 3 — Visual mail-routing rule editor + Sieve sync

**3a [BLOCKER] — Self-hosted "separate personal script" breaches the ADDITIVE constraint outright.** D3 pushes to a separate script `thundercrab_personal` and frames it as coexisting via "sieve_before → personal active → sieve_after." But managesieve SETACTIVE is single-active-script (managesieve.rs:34, and SERVER-COUPLING.md:95 rates this Strategy C "brittle; SETACTIVE is single-script"). `put_active_script` does PUTSCRIPT **+ SETACTIVE** (managesieve.rs:146-159). Activating `thundercrab_personal` **deactivates Mailroom's script** — that is clobbering the baseline's effect, the #1 hard constraint ("never clobber an existing server script"). The "coexist" framing is the bug. Coexistence requires Sieve `include` support, which the doc explicitly says varies and is unbuilt. On self-hosted servers this design as written violates the constraint it claims to honor.

**3b [MAJOR/correct] — D3 is the ONLY design that gets the safety-gate right.** It correctly identifies that reusing `apply_suggestion` for *user* rules would silently demote them: `apply_suggestion` force-rewrites `origin=Federated` and clamps `score` to `1..=49` (safety.rs:82-93, confirmed). D1 and D4 are silent on which gate user-edited rules pass; D3's proposed *separate* `validate_user_rule` (reuse `is_safe_match` floor, keep origin=User, keep ≥100 band) is the right shape. This is a genuine strength and exposes a gap in the others.

**3c [MAJOR] — `evaluate()` is confirmed MISSING and is a hard prerequisite, not a feature.** D3's "test against recent" and "why is this here?" both depend on `core::eval::evaluate`, which does not exist anywhere in core/suggestions (verified; matches SERVER-COUPLING.md:46 "MISSING — port per FFI-API-SPEC §7"). D3 correctly flags it as a prerequisite. Note the *cheaper* "why is this here?" exists for free: the server already writes `X-PlausiDen-Category`, which is already in `other_headers` from `fetch_headers` (SERVER-COUPLING.md:124-128) — D3 should prefer that header-read path over porting `evaluate` for the explainer.

**3d [BLOCKER] — D3 removes the deliberate Android no-pushSieve guardrail without acknowledging it.** The Android `ThunderCrabRepository` *intentionally* has no `pushSieve` method: "there is deliberately no pushSieve method here (AVP-2 guardrail, spec §6)... no live push" (ThunderCrabRepository.kt:60-100). D3 adds `pushPersonalSieve(confirmClobber)` and `syncStatus()` to the Repository. Even though `push_sieve` exists in the FFI (lib.rs:767), the Android contract walls it off on purpose. D3 must justify reopening this guardrail and gate it behind the same explicit operator-consent + throwaway-account discipline the roadmap requires — it currently treats the Repository as a blank slate.

**3e [MINOR] — LISTSCRIPTS/GETSCRIPT genuinely absent.** D3's no-clobber preflight needs both; managesieve.rs:32-34 confirms neither exists. Correctly scoped as new work.

## Design 4 — Layout Customization

**4a [MAJOR/positive] — Best-fitting design for its scope.** The frozen `ThundercrabTheme(darkTheme, amoled, dynamicColor, content)` signature is verified exactly (Theme.kt:27-32). The flat-typed `FfiLayoutPrefs` seam matches the codebase convention (vs D1's blob). The "preview lines ≠ body snippet → reinterpret as subject-wrap lines" reframing correctly respects the no-body invariant. Account-keyed `layout_prefs` is the right isolation primitive.

**4b [MINOR] — "FolderListScreen already imports Icons.Filled.Settings" is true but the hook is taken.** Verified: FolderListScreen.kt:22 imports it. But the screen's lambda is `onOpenSuggestions` (line 51) and the IconButton is wired to *suggestions* (line 60) — the Settings glyph is imported, not yet a settings entry point. D4's "the affordance hook is already present" overstates; it's an import, not a wired route. Minor, but the design leans on it.

**4c [MINOR] — Whole-document LWW is honestly scoped, but shares the multi-device divergence gap.** D4 explicitly chooses whole-doc LWW and defers server sync (offline-first), which is defensible for a scalar/enum blob. But the `FolderOverlay` vecs (pinned/hidden/order) have the same within-collection concurrent-edit loss as D1-1d once sync lands. D4 at least flags it (open_question on cross-device divergence). Acceptable for v1 *because* sync is deferred; must not ship the sync half with whole-doc LWW over the folder vecs.

## Flexibility / "all necessary controls" gaps the user asked for
- **No per-rule "test/dry-run before it touches the server" is universally present** — only D3 has it, and it depends on the missing `evaluate()`. The header-read "why is this here?" (free, via `X-PlausiDen-Category`) is absent from D1/D2/D4.
- **No undo/restore for destructive folder delete** beyond a confirm dialog (D2) — given IMAP delete can cascade a subtree, a "deleted folders are gone server-side" warning is present but no soft-delete/recovery affordance.
- **No export/import of the whole profile as a user-portable file** — D1's profile is device/server-synced but there's no "back up my personalization" control, which a "flexible, all controls" mandate implies.
- **Theme/density editable offline, but folder-overlay needs a live session** (D4 4b open_question) — acceptable, but the controls list should make the gating explicit so the user isn't surprised that pin/hide is greyed out pre-connect.

## Bottom line
- **D2 and D4** are buildable largely as written (modulo X1 schema coordination, 2c/4c sync caveats).
- **D1** has two blockers (1a header round-trip break, 1b no base64) that make its chosen storage mechanism non-functional as specified; its sync model (1d) is not actually additive within collections.
- **D3** has the best safety-gate analysis (3b) but a blocker (3a single-active SETACTIVE breaches ADDITIVE on self-hosted) and reopens a deliberate guardrail (3d).
- The **cross-design collisions (X1–X4)** are the highest-value findings: schema version, dual rule stores, FFI shape, and the non-existent local per-user isolation must be resolved *across* the four before any one ships.
